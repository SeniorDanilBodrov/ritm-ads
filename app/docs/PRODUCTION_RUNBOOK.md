# Production runbook

Этот документ нужен дежурному разработчику во время live-пилота. Пользовательский
маршрут описан в [ACCEPTANCE.md](ACCEPTANCE.md).

## Состояния кампании

| Состояние        | Внешние изменения                                | Показы                                      |
| ---------------- | ------------------------------------------------ | ------------------------------------------- |
| Подготовка       | Нет                                              | Нет                                         |
| Черновик создан  | Выключенные объекты записаны и прочитаны обратно | Нет                                         |
| На модерации     | Объявления отправлены Яндексу                    | Нет                                         |
| Готова к запуску | Модерация, бюджет, период и отчёт проверены      | Нет                                         |
| Активна          | Выполнен подтверждённый `Campaigns.resume`       | Возможны                                    |
| Остановлена      | Выполнен `Campaigns.suspend` и read-back         | Нет новых показов после обработки площадкой |

## Перед изменением флага

1. Зафиксируйте commit SHA и версию схемы.
2. Выполните `npm run check` и `npm run production:preflight:strict`.
3. Убедитесь, что `/api/ready` возвращает `ready=true`.
4. Проверьте очередь reconciliation. Нерешённых записей быть не должно.
5. Сделайте backup или точку восстановления Neon.
6. Запишите ожидаемое действие, campaign ID, лимит и критерий успеха.

## Неопределённый ответ API

Таймаут после отправки не означает, что Яндекс отклонил запрос. Ритм сохраняет
такую операцию как `needs_reconciliation` и не повторяет её автоматически.

Порядок действий:

1. Не отправляйте тот же запрос вручную.
2. Запустите inspect/read-back для конкретного action ID.
3. Если объект найден в ожидаемом состоянии, сохраните результат сверки.
4. Если состояние отличается, остановите сценарий и разберите журнал.
5. Новый write-запрос допустим только после однозначного завершения прежнего.

## Budget Guard

Автопилот работает только при свежих, точно привязанных данных. Он не повышает
общий бюджет бизнеса. Перераспределение меняет лимиты двух кампаний так, чтобы
их сумма осталась прежней.

Применение выполняется в безопасном порядке: сначала уменьшается лимит донора,
затем растёт лимит получателя. При откате сначала уменьшается получатель, затем
восстанавливается донор. Частичный отказ поэтому не увеличивает возможный
общий расход.

Если второй шаг не подтверждён чтением Direct, действие требует сверки. Не
исправляйте лимиты вручную до сохранения внешнего состояния.

## Остановка

Для экстренной остановки используйте suspend-action выбранной кампании. После
ответа проверьте состояние чтением API. Затем выключите:

```text
AUTOPILOT_ENABLED=false
DIRECT_RESUME_PILOT_ENABLED=false
```

`LIVE_ADS_ENABLED=false` закрывает новые платные действия приложения, но сам по
себе не останавливает уже активную кампанию в Яндексе.

## Откат

Откат создаёт новое журналируемое действие. Он не удаляет историю. Поддержаны:

- возобновление кампании, которую остановил Ритм, после свежей проверки;
- обратное перераспределение лимитов;
- удаление выключенного черновика варианта Б до трафика;
- остановка проигравшего варианта после финального A/B-решения.

Потраченные средства не откатываются. Если после исходного действия появились
новые данные или ручные изменения в Директе, сервер может отклонить откат.

## Worker

Веб-процесс содержит локальный таймер, но на Render Free он засыпает. Источником
регулярных пробуждений служит Neon schedule-trigger:

```text
Neon Function -> POST /api/internal/autopilot/tick -> очереди PostgreSQL
```

Маршрут принимает bearer из `AUTOPILOT_WORKER_TOKEN`. Ответ 200 подтверждает
только выполнение tick. Проверьте созданные jobs и их итоговые состояния.
Production-trigger `ritm-autopilot-every-15-min` вызывает функцию
`autopilotcron` каждые 15 минут. Если `AUTOPILOT_ENABLED=false`, функция будит
чтение и очереди, но optimizer не применяет изменения к рекламе.

## Ежедневная проверка во время пилота

- `/api/health` и `/api/ready`;
- jobs в `failed`, `running` дольше lease и `needs_reconciliation`;
- свежесть Direct Report и данных обращений;
- сумма лимитов активного портфеля;
- расход относительно общего предела;
- действия optimizer и их read-back;
- решение модерации и статус объявлений.

При расхождении источников автопилот должен остановиться и объяснить причину, а
не выбирать удобное значение.

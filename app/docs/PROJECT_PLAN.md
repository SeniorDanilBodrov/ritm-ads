# План доведения «Ритма» до приемки

Актуален на 29 октября 2026 года. Главный принцип: сначала воспроизводимая и безопасная операция, затем реальный рекламный кабинет, и только после этого автоматизация с денежным риском.

Пилот этапа 2 завершён. Этапы 3 и 5 готовы на уровне закрытых безопасных контуров и требуют внешней приёмки; активная разработка сосредоточена на фактической аналитике и независимой приёмке этапов 4 и 6. Этап 1 встроен как локальная опция: реальный SD 1.5/OpenVINO-прогон прошёл через очередь «Ритма», подготовил JPEG 1200 × 900 и оставил его несогласованным. Прежняя оценка 21–34 рабочих дня была сделана до пилотов и фонового сбора данных; её нельзя автоматически считать актуальным остатком. Реальный трафик и проверка заказчиком могут занять дополнительное время.

Оценка при плотной совместной работе с Codex: **12–20 рабочих дней активной разработки и локальной проверки** оставшихся этапов. Календарно для полной независимой приемки разумно закладывать **3–6 недель** при оперативных ответах владельца и доступных внешних сервисах. Реальный трафик, требования площадки к маркировке и внешнее подтверждение не ускоряются написанием кода. Это диапазон, который нужно уточнять после каждого подтвержденного внешнего сценария, а не гарантия срока.

## Этап 1 — выбранный вариант генерации

Обновлённое решение владельца проекта от 01.11.2026: отказаться от Cloudflare и использовать Stable Diffusion 1.5 INT8 под OpenVINO. Готовый репозиторий `OpenVINO/stable-diffusion-v1-5-int8-ov` занимает около 2,14 ГБ и распространяется по CreativeML Open RAIL-M. Генерация не публикует ассеты и не изменяет рекламу без отдельного ручного согласования.

### Уже реализовано

- HTTP-адаптер локального FastSDCPU/OpenVINO API для `OpenVINO/stable-diffusion-v1-5-int8-ov`;
- долговечная очередь SQLite с lease, тремя попытками и экспоненциальной задержкой;
- идемпотентность по бизнесу и ключу запроса;
- лимит запросов на один бизнес за скользящие 24 часа;
- проверка JPEG/PNG, ограничение размера, SHA-256 и атомарное файловое хранилище;
- структурированный рекламный бриф: цель, сцена, аудитория, три визуальных подхода и четыре формата Директа;
- серверная подготовка непрозрачного JPEG 4:3, 1:1, 16:9 или 3:4 до 4 МБ, сохранение размеров и SHA-256;
- статусы, предпросмотр и отдельное ручное согласование;
- локальная генерация доступна и в демо с тем же дневным лимитом; внешние рекламные API не вызываются;
- отсутствие автоматической загрузки в Direct;
- контрактные тесты провайдера, очереди, лимита, повторов и согласования.

### Осталось для завершения этапа

1. **Выполнено:** структурированный бриф проверен настоящим рекламным сюжетом; второй прогон после отраслевого якоря дал корректную сцену и JPEG 1200 × 900.
2. Оценить реальное качество 1:1, 16:9 и 3:4 только для форматов, которые понадобятся конкретной кампании; техническое преобразование всех четырёх форматов покрыто тестом.
3. Проверить выдачу файла в двух независимых пользовательских сессиях.
4. **Выполнено локально:** завершённый несогласованный вариант можно удалить вручную; согласованные и активные защищены. Опциональная автоочистка выключена по умолчанию и включается только явным сроком `CREATIVE_RETENTION_DAYS`.
5. После реального прогона зафиксировать скриншоты и сценарий приемки.

## Этап 2 — первый безопасный write-E2E

**Фактическое завершение 29 октября:** владелец подтвердил один план, объекты созданы в production Direct и сверены. Кампания осталась `OFF/DRAFT`, лимит и период совпали с планом. Подробности и ID — [LIVE_PILOT_2026-10-29.md](LIVE_PILOT_2026-10-29.md). Следующие абзацы описывают подготовку до пилота.

Сейчас реализована предварительная проверка после успешного dry-run. Она читает доступные кабинеты и кампании через Direct API, сверяет план, привязку Метрики, географию, дату и ограничения расходов, сохраняет идемпотентный отчет и показывает препятствия в интерфейсе. Внешних операций записи она не выполняет. Новый шаблон готовит фиксированный периодный бюджет без автопродления и последовательность `campaigns.add → campaigns.suspend → adgroups.add → keywords.add → ads.add`. Остановка должна быть подтверждена до появления объявлений. В мастере можно задать будущие даты и увидеть точные команды JSON. После успешной проверки пользователь может явно подтвердить один план. Подтверждение привязано к отпечатку плана и конкретному подключению, действует 10 минут, сохраняется в журнале и также не отправляет запросы записи. 29 октября проверен новый план для «Кофейни „Ритм“»: период 1–14 ноября, потолок 3 000 ₽, один макет и три ключевые фразы. Локальный dry-run подготовил пять команд с нулем внешних вызовов. Затем production API вернул доступный кабинет `specnazbodroff` в RUB и ноль существующих кампаний; read-only preflight сохранил `ready=true`, 0 замечаний, 2 запроса чтения и 0 записей. Совместимость с конкретным кабинетом и минимальными лимитами Директа при записи все еще не подтверждена. Следующий шаг — ограниченный write-E2E по отдельному согласию владельца.

API-поля и ограничения сверены с первичными источниками: [TextCampaign.add](https://yandex.ru/dev/direct/doc/ru/campaigns/add-text-campaign), [Campaigns.suspend](https://yandex.ru/dev/direct/doc/ru/campaigns/suspend), [бюджет на период](https://yandex.ru/support/direct/ru/strategies/period-budget). Ответ Direct при реальном `add` может выявить дополнительные ограничения конкретного кабинета; локальный preflight этого не доказывает.

После read-only прогона исполнитель усилен: перед отправкой он проверяет отпечатки и порядок пяти команд, после `suspend` отдельно читает `Campaigns.get` и требует состояния `SUSPENDED`, а для каждого `add` требует полный набор ID без ошибок. Если остановка не подтверждена, группы и объявления не создаются. Контрактные тесты проходят; фоновый worker по-прежнему исполняет только dry-run.

Следующий локальный шаг выполнен: добавлена таблица `direct_executions` с единственным активным исполнением на бизнес. Одноразовый журнал открывается только для свежего подтвержденного плана при явном программном допуске, сохраняет намерение до каждого вызова и подтвержденные ID сразу после ответа. Неполный или неопределенный результат, а также перезапуск переводят исполнение в `needs_reconciliation` без автоматического повтора. Завершение требует полного чтения кампании, группы, фраз и объявлений по сохраненным ID. HTTP-маршрут и отдельная кнопка создания выключенной кампании добавлены, но серверный допуск `DIRECT_WRITE_PILOT_ENABLED` выключен по умолчанию и требует production-режим, постоянный ключ и `APP_ORIGIN` с HTTPS либо HTTP на localhost. Сквозной HTTP-тест с подставным Direct-клиентом прошел; реальных записей в Директ не было.

При срочном сроке в двое суток текущий критический путь описан в [48H_PLAN.md](48H_PLAN.md). Полная production-приемка все еще зависит от доступов, реального трафика и внешней проверки; локальные тесты не заменяют эти доказательства.

До его запуска должны одновременно выполняться условия:

- `LIVE_ADS_ENABLED=false` остается значением по умолчанию;
- выбран отдельный production-кабинет и логин;
- письменно определено, какие выключенные объекты разрешено создать;
- показы, стратегия с расходом и автозапуск запрещены;
- заполнены счетчик/цель, регион, сайт и контактные данные;
- задан нулевой или минимально допустимый потолок риска и план очистки;
- пользователь видит итоговый JSON-план и явно подтверждает одну операцию;
- после создания сервис читает объекты обратно, сохраняет ID и предлагает остановку/архивацию.

## Этапы 3–5 — рабочий рекламный цикл

**Состояние на 30 октября:** для пункта 2 подготовлен закрытый `resume`-пилот, для пункта 3 — закрытое уменьшение лимита `TEXT_CAMPAIGN`, а для пункта 4 — безопасное создание выключенного варианта Б и раздельный read-only отчёт по двум ID. Вариант создаётся только в сверенной выключенной группе, журналируется до единственного `Ads.add`, читается обратно и при неопределённом результате не отправляется повторно. Модерация и проверка готовности после этого учитывают оба объявления. Отчёт не объявляет победителя до конца зафиксированного периода и проверяет срок, выборку, баланс показов и интервалы CTR. Все write-флаги по умолчанию выключены; реальный вариант Б этим этапом не создавался.

Порядок включения действий:

1. Только чтение статистики и shadow-рекомендации.
2. Ручное pause/resume существующего объекта.
3. Уменьшение лимита или перераспределение только неиспользованной части.
4. A/B с ручным запуском и фиксированным сроком.
5. Компенсирующий откат.
6. Ограниченная автоматизация одного типа действия.

Каждый уровень включается только после успешной сверки предыдущего. Автоматическое увеличение общего бюджета не входит в первый production-релиз.

## Этап 6 — независимая приемка

- работающее развертывание и production-конфигурация; локальная проверка может идти через HTTP localhost;
- PostgreSQL или обоснованное сохранение SQLite с одним инстансом и проверенным backup/restore;
- журнал ошибок без токенов и персональных данных;
- health/readiness, безопасные агрегаты и CLI-код для мониторинга реализованы; остаётся подключить внешний канал оповещений на выбранной платформе;
- ротация ранее раскрытого Yandex Client Secret;
- данные рекламодателя и маркировка до включения показов;
- исследование рынка и ограничений через интервью или профильную литературу/обучение, с зафиксированными выводами;
- чек-лист установки чужих Google/Yandex OAuth credentials без изменения кода;
- полный приемочный протокол: создание, управление, статистика, бюджет, A/B, откат.

## Что потребуется от владельца проекта

Для генерации: запустить FastSDCPU API и задать `LOCAL_IMAGE_API_URL`; для Docker используется `http://host.docker.internal:8000`.

Перед этапом 2: решение о тестовом кабинете, разрешенных выключенных объектах и явное подтверждение безопасного production-write теста.

Перед этапом 6: независимое развертывание, production OAuth-приложения, новый Yandex Client Secret и данные рекламодателя для маркировки. Собственный домен и HTTPS не являются отдельными пунктами нового ТЗ. Для публичного Google OAuth адрес возврата должен отвечать правилам Google; HTTP localhost допускается. Интервью не требуется, если исследование проведено по литературе или обучению.

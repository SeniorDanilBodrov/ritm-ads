# Ритм

Веб-приложение управления рекламой малого бизнеса. Версия 0.1 выполняет полный пользовательский цикл **на тестовых данных**: создание бизнеса, подготовка текстов, подключение тестовой аналитики, запуск плана, изменение бюджета, симуляция результатов, решения оптимизатора, эксперимент и журнал с откатом.

Это еще не готовый к эксплуатации рекламный сервис из обновленного задания. Реальные рекламные операции закрыты в конфигурации по умолчанию. Для обычного бизнеса уже доступны редактор плана и долговечный dry-run: формируются команды создания кампании, группы, ключевых фраз и объявлений, но во внешний API отправляется 0 write-запросов. Новый локальный планировщик на Ollama/Qwen 3.5 4B подготавливает аудитории, фразы, объявления и гипотезы только как структурированное предложение; Direct API не вызывается, пока план не пройдет отдельную проверку. Настройка: [docs/LOCAL_TEXT_MODEL.md](docs/LOCAL_TEXT_MODEL.md). Генерация изображений и видео временно выключена из пользовательского сценария. Google-вход и OAuth Яндекса проверены с реальными учетными записями. Одобренный Direct API вернул кабинет `specnazbodroff`, пустой список кампаний и пустой отчет; Метрика вернула реальные счетчики, цели и статистику, после чего счетчик `113772654` и цель `674240488` были связаны с бизнесом. Для проверяющего подготовлена [краткая инструкция передачи](docs/SUBMISSION.md). Изменения новой редакции задания: [docs/REVISED_REQUIREMENTS.md](docs/REVISED_REQUIREMENTS.md). Дальнейший план: [docs/PROJECT_PLAN.md](docs/PROJECT_PLAN.md). Подробная матрица реализации: [docs/STATUS.md](docs/STATUS.md).

## Быстрый запуск

Нужен Node.js 24.14.1 или совместимый Node 24 с `node:sqlite` и npm. Локальная
разработка использует SQLite; production поддерживает PostgreSQL через
`DATABASE_URL`.

```sh
cd app
npm ci
npm run build
npm start
```

Открыть **http://localhost:4310**, нажать **Попробовать демо**. Ключи и аккаунты не нужны. Данные сохраняются в `app/data/ritm.sqlite`, не в localStorage. Каждый новый браузерный сеанс получает отдельный демонстрационный бизнес. История остается после обновления страницы и перезапуска сервера; для доступа нужна действующая cookie сессии.

Точно используйте `localhost`, а не `127.0.0.1`: сервер проверяет Origin для операций записи. Для другого адреса задайте `APP_ORIGIN`.

## Что проверить в демо

1. Откройте обзор: расход, обращения, подтвержденные клиенты и бюджет рассчитываются на сервере.
2. Нажмите **Смоделировать день**. В историю попадет перераспределение неиспользованного лимита. Это один искусственный день, а не фактически прожитый календарный день.
3. Откройте историю и отмените перераспределение. Если после него появились новые данные, сервер отклонит откат с объяснением.
4. Измените бюджет. Попытка установить его ниже уже потраченного расхода с резервом будет отклонена.
5. В экспериментах нажмите симуляцию 17 раз: начальный тест достигнет 21-го тестового дня и выдаст итог. Минимальная выборка и правило анализа фиксированы; до финального дня победитель не объявляется.
6. В настройках добавьте бизнес. Пройдите анкету, подключите тестовую аналитику, согласуйте текст на вкладке объявлений, запустите тестовый план в разделе рекламы.
7. Экспортируйте CSV из истории. Поля начинающиеся с символов формул экранируются.
8. При настроенном Python откройте **Аналитик → Проанализировать**. Результат содержит основания и рекомендации, но не изменяет кампании. После изменения данных появляется предупреждение об устаревшем анализе.
9. Откройте **Сверка данных**. Получите тестовый отчёт, затем «Проверить расхождение»: появятся два отдельных снимка на 197,00 ₽ и 322,00 ₽, а расход обзора останется 197 ₽. Сценарий ожидания проверяет, что незавершённый отчёт не сохраняется как нулевой.

Демо не обращается к рекламным API и не запускает локальную модель. Иллюстрации на карточках созданы CSS и служат только для предпросмотра. В рабочем бизнесе при запущенном FastSDCPU API можно отдельно создать настоящий растровый ассет; он не отправляется в Direct автоматически. Тексты формируются по шаблонам, без подключенной языковой модели. Экспериментальные выборки отдельные и синтетические; не суммируйте их с общей статистикой.

## Разработка и проверки

```sh
npm test
npm run build
```

`npm run check` выполняет обе команды. Сервер использует ESM JavaScript, интерфейс — React и TypeScript. В тестах проверяются транзакции, изоляция, CSRF, повторные команды, бюджет, откат, эксперимент, шифрование, очередь dry-run, зависимости удаленных ID, повторы, сверка и поведение провайдеров. Сетевые контракты проверяются подставными ответами; это не доказательство совместимости с реальным кабинетом.

Яндекс отключил API-песочницу 15 июля 2026 года. Production API проверен на чтение, а согласованный пилот создал выключенные кампании и связанные объекты без показов. Штатный путь «проверка → выключенный черновик → модерация → запуск → остановка/лимит» управляется состоянием бизнеса в интерфейсе и не требует переключать флаги между этапами. Каждая запись одноразовая, подтверждается чтением Direct и не повторяется при неопределённом ответе. Уменьшенный лимит можно явно вернуть только к исходному утверждённому бюджету, пока кампания остановлена. Read-only проверка бюджета отдельно показывает сохранённый отчёт о расходе; такой отчёт не равен текущему остатку. Необратимая архивация и экспериментальные A/B write-действия остаются за отдельными pilot-флагами.

Результаты по каждому FR/NFR и приемочному критерию — [docs/VERIFICATION.md](docs/VERIFICATION.md). Непроверенные требования не отмечены выполненными.

Пошаговый сценарий для независимого проверяющего: [docs/ACCEPTANCE.md](docs/ACCEPTANCE.md).

## Python-аналитик

Нужен Python 3.10+ без дополнительных пакетов. В `.env` задайте абсолютный путь `PYTHON_EXECUTABLE` к интерпретатору и оставьте `AI_PROVIDER=rules`. Перезапустите сервер. Без Python остальные функции демо доступны, кнопка анализа отключена.

Проверки Python из каталога `app`:

```sh
python -m unittest discover -s ai -p 'test_*.py' -v
```

Для проверки связки Node → Python экспортируйте `PYTHON_EXECUTABLE` в окружение перед `npm test`. В PowerShell: `$env:PYTHON_EXECUTABLE='C:\path\to\python.exe'`. Если переменная не задана, этот один интеграционный тест явно пропускается; остальные выполняются. Сам `npm test` не загружает `.env`.

`rules` — воспроизводимый baseline, не нейросеть. `ollama` — опциональный адаптер локальной LLM: задайте `AI_PROVIDER=ollama`, `OLLAMA_URL=http://127.0.0.1:11434` и `OLLAMA_MODEL` с именем уже установленной модели. Приложение не скачивает и не запускает модели. HTTP-контракт сверялся с [Ollama Chat API](https://docs.ollama.com/api/chat) и [Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs); настоящая модель в этой среде не запускалась. В Docker loopback относится к самому контейнеру, не к хосту; готовой схемы размещения Ollama в compose нет.

Аналитику передаются только ID, статус и числовые показатели, не токены/анкета/содержимое сайта. Ответ ограничен восемью предложениями. Проверяются схема, принадлежность ID и допустимость действия по данным. Свободный текст модели не становится доказанным фактом. Внешние endpoint и перенаправления запрещены. При ошибке LLM возвращается ошибка, а не незаметная подмена нейросети правилами. Один анализ на пользователя, максимум четыре одновременно на процесс; 40 секунд на выполнение. Это не распределенный rate limiter. Устаревший результат не сохраняется; повтор успешного запроса с тем же ключом возвращает прежний ответ.

Для разработки интерфейса можно запустить `npm run dev:ui` вторым процессом. Задайте серверу `APP_ORIGIN=http://localhost:5173`, чтобы пройти проверку Origin; callbacks OAuth также должны соответствовать выбранному origin. Для демонстрации предпочтителен собранный интерфейс на порту 4310.

В реальном бизнесе раздел «Подключения» читает доступные счётчики и цели Метрики, проверяет выбранные объекты повторным запросом и выдаёт готовый код для `<head>` и точный вызов JavaScript-события после успешной заявки. Если цель не событийная или домен не совпадает, интерфейс показывает предупреждение вместо ложного статуса готовности.

Финальная production-проверка создания выключенных объектов Директа описана в [`docs/LIVE_PILOT_2026-10-31.md`](docs/LIVE_PILOT_2026-10-31.md). Кампания, группа, три фразы и объявление созданы и повторно прочитаны; кампания осталась в состоянии `OFF / DRAFT`.

## Google и Яндекс

Google redirect URI: `<APP_ORIGIN>/auth/google/callback`. Используются authorization code, PKCE, одноразовый state и nonce, серверная проверка подписи/issuer/audience ID token через JWKS. Вход проверяет подтверждение email; идентичность хранится по `sub`, а не по адресу email.

Яндекс использует фиксированный redirect URI `https://oauth.yandex.ru/verification_code`. «Ритм» открывает авторизацию в новой вкладке: пользователь копирует показанный Яндексом одноразовый код и вставляет его в раздел «Подключения». Код, state и cookie живут десять минут и привязаны к текущей сессии и выбранному бизнесу. Приложение должно иметь разрешение Direct API и подходящие read-разрешения Метрики. Токен шифруется AES-256-GCM с привязкой к business ID. Подключать реальный кабинет к демобизнесу запрещено. Параметр `YANDEX_SANDBOX=true` намеренно останавливает сервер: после официального отключения песочницы нельзя незаметно перенаправлять тестовый сценарий на production.

### Включение автономного режима

Обычная локальная приёмка остаётся без платных действий: `LIVE_ADS_ENABLED=false`. Для отдельного production-окружения с настоящими рекламными кабинетами задайте HTTPS `APP_ORIGIN`, постоянный `TOKEN_ENCRYPTION_KEY`, `NODE_ENV=production`, `LIVE_ADS_ENABLED=true` и `AUTOPILOT_ENABLED=true`, затем выполните:

```sh
npm run production:preflight:live
```

Автопилот читает свежие раздельные данные Direct и Метрики. Он останавливает подтверждённо убыточную кампанию. Если две активные кампании относятся к одному кабинету и одной цели Метрики, срезы подтверждают разницу в CPA, а у донора есть неиспользованный остаток, worker переносит этот остаток победителю. Сначала он уменьшает лимит донора, затем повышает лимит получателя на ту же сумму и читает оба значения из Direct. Общий лимит портфеля не растёт. Неоднозначную или частично отправленную запись worker не повторяет.

Для проверки интеграции войдите через Google, создайте бизнес и откройте «Подключения». Можно получить список кампаний, отчет Директа, выбрать доступные счетчик и цель Метрики, запросить их статистику, а также отключить Яндекс с попыткой отзыва токена. На вкладке «Моя реклама» можно собрать план и выполнить dry-run. Кампании не меняются. Данные ответов не смешиваются с демонстрационными показателями. При временном таймауте Директа уже полученный токен сохраняется зашифрованным, а проверку кабинета можно повторить без нового OAuth; невосстановимая ошибка восстанавливает предыдущее подключение. Access- и refresh-токены хранятся только зашифрованно; перед истечением срока или после ошибки авторизации выполняется один обмен refresh-токена по [официальному контракту Яндекс OAuth](https://yandex.ru/dev/id/doc/ru/tokens/refresh-client). Конкурентные запросы объединяются, новый refresh-токен сохраняется атомарно, а при `invalid_grant` интерфейс просит подключить Яндекс заново. Для agency-аккаунтов требуется дополнительный адаптер AgencyClients; сейчас предназначено для прямого рекламодателя. Проверка фактической установки счетчика на произвольном сайте еще не реализована.

## Устройство

- `server/db.js`: версионированная схема SQLite, `BEGIN IMMEDIATE`, атомарная запись команды/состояния/событий. WAL, busy timeout, связанные записи.
- `server/engine.js`: детерминированная симуляция, бюджет в целых копейках, перераспределение, контрольная версия объекта, интервалы Уилсона и фиксированный момент проверки эксперимента.
- `server/app.js`: JSON API, валидация Zod, принадлежность бизнеса, session cookie, Origin и custom-header защита операций записи.
- `server/oauth.js`, `providers.js`, `security.js`: OAuth, прямые HTTP-клиенты, отзыв токена, отчеты и шифрование.
- `server/direct.js`, `server/direct-execution.js`, `server/direct-lifecycle.js`, `server/direct-budget.js`, `server/direct-budget-action.js`, `server/portfolio-reallocation.js`, `server/direct-ab.js`, `server/direct-ab-action.js`, `server/direct-ab-decision.js`: схема реального плана, dry-run, одноразовое создание выключенной кампании, проверяемая остановка, лимиты портфеля, перенос остатка между двумя активными кампаниями с read-back, безопасное создание варианта Б и компенсирующее A/B-действие.
- `server/creative-images.js`: локальный Stable Diffusion 1.5 INT8/OpenVINO, очередь генерации, рекламные форматы Direct, лимиты, хранение, ручное согласование, защищённое удаление и опциональная retention-очистка.
- `server/operations-monitor.js`: обезличенные HTTPS webhook-оповещения только при смене операционного состояния.
- `server/reports.js`: долговечная очередь отчётов Direct, строгая нормализация TSV, снимки источника и сверка исправлений.
- `server/advisor.js`, `ai/advisor.py`: ограниченный read-only Python-процесс; baseline и адаптер локальной LLM с валидацией.
- `src/`: адаптивный интерфейс, формы, таблицы, график, предпросмотр текстов.
- `tests/`: автоматические проверки без внешних учетных данных.

SQLite выбран для воспроизводимой локальной проверки без внешних сервисов; многорепличное production-развертывание требует отдельной архитектуры очереди. Реализованы устойчивая очередь фонового анализа сохраненных данных (`server/worker.js`), очередь чтения Reports Direct (`server/reports.js`) и очередь команд Direct в режиме dry-run (`server/direct.js`). После явного HTTPS production-допуска live-worker регулярно запрашивает отчёты, выполняет shadow-сверку, применяет защитную остановку и может перенести подтверждённый свободный остаток между двумя кампаниями одного кабинета. Реальный E2E с платным кабинетом для этого сценария ещё нужен.

### Фоновый анализ

В разделе «Аналитик» включите фоновый анализ для выбранного демобизнеса. Сервер проверяет очередь каждые 5 секунд: первый анализ запускается при наличии кампаний, следующие — при изменениях данных и не раньше часа после предыдущего успешного задания. Открытая вкладка не нужна, работающий Node-сервер и Python нужны. Обновите страницу, чтобы увидеть результат и статус задания. По умолчанию расписание выключено; тестовое расписание после браузерной проверки также выключено.

Задания переживают перезапуск благодаря SQLite. Обработка берет lease на 60 секунд; устаревший обработчик не может сохранить результат поверх нового. Ошибки повторяются через 15 и 30 секунд, максимум три попытки. После исчерпания повторов требуется исправить конфигурацию и выключить/включить расписание. При изменении снимка результат отменяется, а не перезаписывает новые данные. Результат, событие и завершение задания фиксируются одной транзакцией. Отключение отменяет ожидающие задания и запрещает сохранение результата выполняющегося. Одновременно выполняется один фоновый Python-процесс дополнительно к максимум четырем ручным анализам. Это локальный shadow-режим: он не вызывает рекламные API, не продвигает тестовый день, не меняет лимиты и не доказывает выполнение FR-15 о сборе статистики и бюджетном стороже.

### Сверка отчётов Direct

Раздел «Сверка данных» запускает отдельное read-only задание. Сервер переживает закрытие вкладки и перезапуск, повторяет временные ошибки не более трёх раз, учитывает `retryIn` для ответов 201/202 и прекращает ожидание после 30 проверок. В снимок входят исходный TSV, SHA-256, нормализованные строки, итог, период, логин, валюта, НДС и request ID. Одинаковый исходник не дублируется; исправленная версия сравнивается с предыдущей внутри того же источника, логина и периода. Подробные гарантии и ограничения: [docs/REPORTS.md](docs/REPORTS.md).

Отчёты сейчас запрашиваются вручную, только в RUB и с НДС. Максимум — 2 МиБ и 10 000 строк. Сумма округлённых строк может отличаться от агрегата площадки; «консервативная оценка» интерфейса — только сигнал сверки, не фактический расход и не лимит. Для сохранённого A/B-плана доступен отдельный `AD_PERFORMANCE_REPORT`, ограниченный двумя ID объявлений. Он не подменяет кампанийный отчёт при проверке общего расхода. Данные отчётов намеренно не меняют обзор, кампании или бюджет.

Shadow-сверка читает общесайтовую Метрику и отдельный несемплированный срез по точному ID кампании Директа через `ym:s:lastsignDirectClickOrder` с атрибуцией `lastsign`. Только второй срез может дать `campaignGoalReaches` и расчётный CPA; общесайтовые цели никогда не приписываются кампании. Источник контракта: [официальный справочник группировок Метрики](https://yandex.ru/dev/metrika/ru/stat/attrandmetr/dim_all). Результат остаётся read-only shadow-сводкой и не является автоматическим разрешением менять бюджет.

## Развертывание

Подготовлены и проверены `Dockerfile` и `compose.yaml`. Полная локальная приёмка выполняется командой `npm run acceptance`; вариант `npm run acceptance:docker` дополнительно пересобирает образ и выполняет строгий production-preflight внутри Compose. Runtime smoke подтвердил `ok=true`, `ready=true`, `degraded=false`, `liveLaunch=false`. Нагрузочный smoke на 300 запросах при concurrency 25 завершился без ошибок: p95 40 мс при пороге 500 мс. Backup/restore, ops-check, ops-load, production-preflight и acceptance runner входят в runtime-образ. Для локальной проверки используйте постоянный ключ, `APP_ORIGIN=http://localhost:4310` и постоянный том. Собственный домен и HTTPS не входят в отдельные критерии нового ТЗ. Если сервис будет доступен публично и использует Google OAuth, адрес возврата должен соответствовать правилам Google; тогда требуется HTTPS. Не устанавливайте произвольный `trust proxy` в Express: сначала определите доверенные адреса прокси.

В репозитории есть Blueprint для Render в корне проекта. Перед первым deploy задайте в панели Render `DATABASE_URL` из Neon, `APP_ORIGIN` с адресом Render и `TOKEN_ENCRYPTION_KEY`. Без этих переменных production не стартует. `POSTGRES_ASYNC_PILOT` оставлен `false`: проверенный пилот хранит пользователей, бизнесы и отчёты в PostgreSQL, но пока не покрывает все маршруты текущего SQLite-приложения. Включать его можно только на отдельном preview-сервисе после `npm run acceptance:postgres-pilot` с `DATABASE_SMOKE_TEST=true`; эта проверка создаёт и удаляет тестовые записи. Платные действия и автопилот остаются выключенными отдельными флагами.

По умолчанию Dockerfile использует официальные Debian-зеркала. Для медленной или ограниченной сети адреса можно заменить только на время сборки: `docker compose build --build-arg DEBIAN_MIRROR=http://ваше-зеркало/debian --build-arg DEBIAN_SECURITY_MIRROR=http://ваше-зеркало/debian-security`. Репозиторий должен публиковать корректно подписанные `InRelease`; не отключайте проверку подписей.

```sh
docker compose build
docker compose run --rm --no-deps app node scripts/production-preflight.js --strict
docker compose up -d
docker compose logs -f app
```

Порт контейнера опубликован только на loopback сервера. Прокси должен направлять запросы на 127.0.0.1:4310. База хранится в томе `ritm-data`. Публичная публикация и домен не настроены: адрес текущего результата локальный.

## Резервные копии и обслуживание

Приложение создаёт консистентную копию SQLite через `VACUUM INTO`, проверяет `quick_check` и внешние ключи и сохраняет рядом SHA-256-манифест:

```sh
npm run db:backup
npm run db:verify -- --manifest ./data/backups/ritm-YYYYMMDD-HHMMSS.manifest.json
npm run db:restore -- --manifest ./data/backups/ritm-YYYYMMDD-HHMMSS.manifest.json --target ./data/restored/ritm.sqlite
```

Путь базы задаётся `DATABASE_PATH`, каталог копий — `BACKUP_PATH`. Восстановление намеренно разрешено только в новый файл и отказывается перезаписывать существующую БД. Для переключения остановите приложение, сохраните прежний каталог и укажите восстановленный файл в `DATABASE_PATH`. Ключ `ENCRYPTION_KEY` в backup не входит: храните его отдельно, иначе зашифрованные OAuth-токены нельзя будет прочитать. Саму копию защищайте как пользовательские данные. В Docker те же команды запускаются через `docker compose exec app npm run ...`; каталог `/app/data` находится в постоянном томе.

`GET /api/health` — лёгкая liveness-проверка процесса и БД. `GET /api/ready` сверяет версию схемы и возвращает только агрегаты очередей (`pending`, `ready`, `running`, `stale`, `failed`) и количество операций, требующих read-only reconciliation; ID, payload, ошибки и данные бизнесов не раскрываются. Команда `npm run ops:check` выдаёт тот же безопасный снимок напрямую из SQLite и возвращает код `0` для нормы, `2` для degraded и `1` для неготовой БД. При `OPS_ALERT_WEBHOOK_URL` сервер отправляет по HTTPS такой же обезличенный агрегат только при переходе в degraded/unavailable и при восстановлении; здоровый запуск молчит. `degraded=true` не разрешает автоматический повтор write-команды. Ошибки сервера выводятся без payload и токенов. Журнал действий не имеет API удаления и не является криптографически неизменяемым. Нет SLA, планировщика резервирования и полного удаления бизнеса/пользователя — это задачи следующего этапа.

## API

# Независимая приемка безопасного этапа

Документ позволяет проверить текущий результат без доступа к платному кабинету. Он не подтверждает live-запуск рекламы.

## 1. Автоматические проверки

Из каталога `app`:

```sh
npm ci
npm run acceptance
```

Команда последовательно запускает Node/API-тесты, TypeScript и production-сборку, Python-тесты, проверку readiness и `docker compose config` (если Docker установлен), затем сохраняет обезличенный результат в `data/acceptance-report.json`. Для обязательной пересборки контейнера используйте `npm run acceptance:docker`: после сборки он также запускает строгий production-preflight внутри Compose с реальными путями и `NODE_ENV` контейнера. Отдельные команды ниже остаются полезны при диагностике.

```sh
npm test
npm run build
python -m unittest discover -s ai -p "test_*.py" -v
```

На 30.10.2026 актуальный Docker-прогон выполнил **187 Node-тестов и 10 Python-тестов без ошибок**, затем успешно завершил TypeScript-проверку и production-сборку Vite. Локальный прогон выполнил 186 Node-тестов; один необязательный Node → Python тест пропущен без настроенного `PYTHON_EXECUTABLE`. Runtime smoke подтвердил healthy/ready на схеме 22, а ранее выполненные 300 запросов health/readiness при concurrency 25 завершились с 0 ошибок и p95 40 мс. В прогон входят HTTP-контракты Node-сервера, backup/restore, webhook-монитор, жизненный цикл рекламных креативов, точная campaign-ID атрибуция, production-preflight, проверка комплекта сдачи и нагрузочный smoke.

Критичные проверки находятся в:

- `tests/direct.test.js` — структура команд, ссылки на внешние ID, idempotency, lease, повторы, предел попыток и сверка;
- `tests/providers.test.js` — Direct add-методы, Метрика, `revoke_token` и безопасный refresh-запрос;
- `tests/direct-execution.test.js` — журналы write-пилотов, уменьшение лимита, идемпотентность, read-back, неопределённый ответ и восстановление после перезапуска;
- `tests/oauth.test.js` — сохранение токена при таймауте, атомарная ротация, single-flight, повтор после auth-ошибки и `reauth_required`;
- `tests/api.test.js` — изоляция бизнеса, CSRF, live-gate, endpoint dry-run и полный контракт Google OAuth: HTTPS callback, state, nonce, S256 PKCE, одноразовость, два разных `sub` и отсутствие сохраненных Google-токенов;
- `tests/reports.test.js` — исходные отчеты, дедупликация и сверка исправлений.
- `tests/backup.test.js` — консистентная SQLite-копия, SHA-256, проверка целостности, восстановление и запрет перезаписи существующей БД.

## 2. Проверка Docker

```sh
docker compose config --quiet
docker compose build
docker compose run --rm --no-deps app node scripts/production-preflight.js --strict
docker compose up -d
docker compose ps
curl http://127.0.0.1:4310/api/health
curl http://127.0.0.1:4310/api/ready
docker compose exec app npm run ops:check
docker compose exec app npm run ops:load -- --requests 300 --concurrency 25
docker compose down
```

Ожидаемый обычный preflight: `PASSED`, ноль ошибок и только ручное напоминание о ротации ранее раскрытого Yandex Client Secret. Он не печатает значения секретов, проверяет production-режим, origin, длину ключа шифрования, постоянную БД, парность OAuth-параметров, выключенные рекламные write-флаги и доступность каталогов базы, backup и ассетов. Ожидаемый health: `ok=true`, `liveLaunch=false`, контейнер в `docker compose ps` имеет статус `healthy`. Для отдельного боевого окружения используйте только `npm run production:preflight:live`: ему требуются HTTPS `APP_ORIGIN`, `LIVE_ADS_ENABLED=true` и `AUTOPILOT_ENABLED=true`; после него health возвращает `liveLaunch=true`. Readiness должен вернуть `ready=true`, совпадающие версии схемы и только агрегированные счётчики. `ops:check` в норме завершится кодом 0; код 2 означает degraded, код 1 — неготовую БД. `ops:load` делает только GET-запросы health/readiness, требует 0 ошибок и p95 не выше 500 мс; это короткий smoke, а не доказательство SLA. `degraded=true` требует проверить `queues.stale` и `reconciliation.required`; он не является разрешением повторить внешнюю запись. Проверенный образ содержит Node 24.14.1 и Python 3.11.2. Файл `.env` должен существовать. Локальный Compose с `APP_ORIGIN=http://localhost:4310` подходит только для безопасной проверки без платных действий; при публичном Google OAuth адрес возврата подчиняется правилам Google.

## 2.1. Проверка backup/restore

```sh
npm run db:backup
npm run db:verify -- --manifest ./data/backups/<имя>.manifest.json
npm run db:restore -- --manifest ./data/backups/<имя>.manifest.json --target ./data/restore-check/ritm.sqlite
```

Ожидается три успешных JSON-ответа с одинаковыми `sha256`, `bytes` и `schemaVersion`. Повторное восстановление в тот же target должно завершиться отказом, не изменив файл. Затем запустите сервис с `DATABASE_PATH=./data/restore-check/ritm.sqlite` и постоянным исходным `ENCRYPTION_KEY`; `/api/health` должен вернуть `ok=true`. Не добавляйте резервные копии и ключ в Git.

## 3. Ручной dry-run

1. Войти через Google и создать обычный бизнес; сайт указывать только при наличии.
2. Подключить Яндекс через одобренное приложение API.
3. В «Подключения» получить счетчики, выбрать счетчик и цель.
4. В «Моя реклама» проверить кабинет, ID региона, аудиторию, бюджет, CPA, объявление и ключевые фразы.
5. Нажать «Проверить без отправки».
6. Обновить состояние и убедиться, что очередь показывает `succeeded`, одну попытку и `вызовов API: 0`.

В базе должна появиться одна запись `direct_changes` и одно задание `jobs.kind=direct_change`. Повтор с тем же `Idempotency-Key` и тем же payload не создает вторую запись. Иной payload с тем же ключом возвращает 409.

## 4. Проверка отключения

1. В «Подключения» нажать «Отключить и отозвать токен».
2. Подтвердить действие.
3. Убедиться, что подключение исчезло, а незавершенные задания отчетов отменены.
4. Если интерфейс сообщает, что внешний отзыв не подтвержден, удалить доступ приложения на странице доступов Яндекс ID. Локальная копия токена уже удалена.

## 5. Что нельзя принимать как выполненное

- создание объектов в реальном Direct без отдельного письменного согласования production-проверки, лимитов и плана очистки тестовых черновиков;
- фактические показы, списания, модерацию и маркировку;
- работу Метрики на произвольном будущем сайте: проверен отдельный тестовый лендинг, но установка счетчика в чужой production-сайт автоматически не выполняется;
- SLA, автоматический планировщик backup и горизонтальное масштабирование. Внешний webhook технических оповещений реализован, но для фактической доставки требуется адрес выбранного сервиса в `OPS_ALERT_WEBHOOK_URL`;
- независимую приемку AC-01…AC-08 только на основании unit-тестов.

## 6. Проверка Direct после отключения sandbox

Яндекс официально отключил песочницу 15 июля 2026 года. Поэтому независимая приемка текущей версии состоит из трех уровней:

1. Production OAuth и чтение API проверены методами `Clients.get`, `Campaigns.get` и Reports.
2. Полный граф команд `campaigns → adgroups → keywords → ads`, разрешение внешних ID, идемпотентность, повторы и сверка проверяются автоматическими контрактными тестами.
3. Пользовательский план выполняется через dry-run: очередь завершается успешно, но число внешних write-вызовов равно нулю.
4. После отдельного подтверждения владельца выполнен ограниченный production-пилот: выключенная кампания, группа, три фразы и одно объявление созданы и сверены по API; периодный лимит подтверждён отдельным чтением. Подробности — в [LIVE_PILOT_2026-10-29.md](LIVE_PILOT_2026-10-29.md).

`YANDEX_SANDBOX` должен оставаться `false`. Значение `true` останавливает сервер с явной ошибкой, а клиент провайдера отклоняет sandbox до сетевого запроса. Автоматического fallback на production нет.

Этот пилот не доказывает работу на реальном трафике или управление расходами. Кампания остаётся `OFF/DRAFT`; тестовый рекламодатель не должен проходить модерацию и запускаться без замены данных и отдельного решения владельца.

### Закрытый пилот уменьшения бюджета

`DIRECT_BUDGET_PILOT_ENABLED=false` по умолчанию. При включении сервер принимает только уменьшение периодного лимита выключенной `TEXT_CAMPAIGN`, требует свежую совпавшую сверку и точное подтверждение кампании и старого лимита. Для начавшегося периода обязателен свежий покрывающий отчёт с расходом не выше нового лимита. Запись журналируется до единственного `Campaigns.update`, затем лимит читается обратно. Неопределённая операция не повторяется автоматически; доступна только read-only сверка. Это контрактно проверено подставным клиентом, но реальный лимит кампании не изменялся.

### Одноразовый запуск после принятия модерации

Код `server/direct-resume.js` и карточка «Возобновление показов» подготовлены, но `DIRECT_RESUME_PILOT_ENABLED=false` по умолчанию. Для запуска нужны настоящие данные рекламодателя и сайт, принятые объявления, открытая оплата, действующий период, периодный лимит с `AutoContinue=NO`, свежий отчёт и явное подтверждение ID, лимита и расходов владельцем. Сервер повторяет чтение Директа перед `Campaigns.resume`, сохраняет действие до записи и отправляет запрос только один раз. Неизвестный ответ оставляет `needs_reconciliation`; повторный запрос не отправляется. Отдельная остановка разрешена после неопределённого результата запуска, если запуск уже не выполняется.

Текущая тестовая кампания №715574939 с вымышленным рекламодателем остаётся `OFF/DRAFT`; её не отправляли на модерацию и не запускали. Даже при включённом флаге её проверка блокирует из-за отсутствия принятой модерации и начала периода.

### Закрытый пилот варианта Б

`DIRECT_AB_VARIANT_PILOT_ENABLED=false` по умолчанию. При включении сервер создаёт ровно одно выключенное объявление-вариант в уже сверенной выключенной группе и требует точного подтверждения ID кампании и контрольного объявления. Для единой перфоманс-кампании используется комбинаторный `ResponsiveAd`, для текстово-графической — `TextAd`. Намерение записывается до единственного `Ads.add`, затем вариант ищется повторным чтением группы. Неопределённый ответ не повторяется автоматически; пользователь может выполнить только read-only сверку. Создание варианта не отправляет объявления на модерацию и не запускает показы. После подтверждённого создания последующие проверки модерации и готовности обязаны видеть оба объявления.

### Закрытый пилот A/B-решения

`DIRECT_AB_DECISION_PILOT_ENABLED=false` по умолчанию. До начала периода и до первого A/B-отчёта операция `rollback_variant` принимает только точный ID сохранённого варианта Б, проверяет `OFF/DRAFT`, удаляет его через `Ads.delete` и подтверждает отсутствие повторным чтением. После финального победителя `apply_outcome` не доверяет выбранному клиентом объявлению: сервер сам вычисляет проигравший ID, останавливает его через `Ads.suspend` и подтверждает `SUSPENDED`. Намерение журналируется до внешней записи. Неопределённый ответ не повторяется; доступна только read-only сверка. Тестовые проверки используют подставной Direct-клиент, реальные объявления этим контуром не изменялись.
